# Dedicated native worker host

This broker needs a dedicated Linux Docker host with gVisor or Kata and a private persistent disk. Railway's non-privileged container environment cannot run this broker's Docker sandboxes: https://docs.railway.com/guides/github-actions-runners#known-limitations. The Railway backend and Vercel frontend remain their existing deployment targets. Never mount a Docker socket into an SDK engine or relax its isolating runtime to make it fit Railway.

The host owner must supply the Linux host/connection, private HTTPS broker origin, approved tenant/model processing records and actual reviewed provider budgets. No host or production native credentials have been provisioned by committing these files. The broker is trusted infrastructure with Docker administration rights; isolate it from unrelated workloads and restrict host administration accordingly.

## Release installation

1. Provision the approved Linux VM and persistent disk. Install the reviewed Docker version and pinned isolating runtime. The certificate records the runtime version actually tested; do not substitute runc. Restrict host ingress to administration from approved networks and private TLS ingress from the application. Block arbitrary public access to callback ports; the trusted gateway must reach host callbacks over its Docker bridge.
2. Create the unprivileged `gravitre-native` account/group and grant only this trusted broker account Docker access. Create `/var/lib/gravitre-native` owned by that account, mode 0700. Install the reviewed release source at `/opt/gravitre` and a Python 3.12 virtual environment at `/opt/gravitre-native/venv`; install `backend/requirements-core.txt` from that checkout. Keep source/venv administrator-owned and read-only to the broker.
3. Pull the three reviewed native images by their exact registry SHA-256 digests. Keep image provenance with the release record. Never use an unreviewed tag as deployment authority.
4. Supply `/etc/gravitre-native/runtime.env` through the approved secret manager, root-readable only (0600). Required names and tenant JSON fields are documented in `docs/engineering/PR581_NATIVE_RUNTIME_IMPLEMENTATION.md`. Use distinct signing, encryption and correlation keys; do not paste values into logs or chat. Point `NATIVE_JOURNAL_PATH` under `/var/lib/gravitre-native`. Keep the correct tenant Langfuse destination and credentials while deletion is unresolved. Do not grant tools, opt in telemetry or fabricate processing permits during host installation.
5. Install `gravitre-native.service` under `/etc/systemd/system`. Review it with `systemd-analyze verify`, then start it through the normal approved release procedure. Preflight checks local runtime/images/disk/configuration only. The existing application is not connected until its `NATIVE_WORKER_URL` and matching signing key are configured for this private broker.
6. Terminate HTTPS at an approved private reverse proxy, forwarding only `/v1/invoke` to loopback port 8091. Restrict access to the application network and retain the signed request boundary. The broker has no public docs or unauthenticated workload path. Do not publish the Docker daemon, journal volume, secrets directory or host callback ports.
7. After the coordinated release, run isolated-tenant acceptance: explicit grants and human approval, actual SDK task and review artifact, browser approval/refusal, revocation/cancellation, network denial, cleanup/restart, opted-in receipt delivery and verified withdrawal. Record exact app/host/image/runtime identities. A service merely starting does not certify these outcomes.

## Recovery

A broker crash must not automatically replay a native operation with an uncertain outcome. Inspect its durable state and reconcile labeled containers first. Gateway/engine deadlines limit orphan work. Preserve the encrypted journal and decrypting keys through recovery. Keep unresolved telemetry destination/deletion records; a changed destination is an explicit failure, never evidence that the old project is erased. Restore the original destination before bounded retries finish, or use an operator-reviewed reconciliation after exhaustion.

The journal uses SQLite WAL. Use one host/private volume with supported local locking, monitored disk capacity and a reviewed encrypted backup/retention plan. SQL payload clearing does not certify physical erasure from WAL, snapshots or backups; handle checkpointing and key destruction through the approved retention process.
