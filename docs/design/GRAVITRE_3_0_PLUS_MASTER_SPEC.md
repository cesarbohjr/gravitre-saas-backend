# GRAVITRE 3.0 PLUS
## Master AI-native UX/UI architecture, design system and frontend transformation specification

## 0. Authority and purpose

This document is the single source of truth for Gravitre 3.0 Plus frontend and product-experience work.

It supersedes all previous standalone design prompts, UI amendments, partial redesign instructions, and isolated page-specific directives.

Do not interpret this specification as permission to immediately redesign production pages.

The first responsibility is to audit, understand, classify, and design the system before broad implementation.

All future frontend work must reference this specification.

Any proposed deviation from an approved design, architecture, interaction rule, or technology decision must be documented and explicitly approved before implementation.

# 2. Product context

Gravitre is an AI operating layer for MSPs and SMBs that connects business systems, data and AI agents into one shared intelligence layer.

Agents can coordinate work across departments, execute workflows, learn from outcomes and operate under centralized governance.

Gravitre includes or is intended to include capabilities such as:

- Ask Gravitre.
- Voice interaction.
- AI agents.
- Multi-agent orchestration.
- Workflow automation.
- Business intelligence.
- Predictive intelligence.
- Knowledge bases.
- Knowledge and relationship graphs.
- Integrations and connectors.
- Model management.
- Human approvals.
- Governance.
- Execution monitoring.
- Continuous learning.
- Marketplace packs.
- Goals and assignments.
- Desktop-style AI windows.
- Mobile/responsive surfaces.

Gravitre is not intended to be:

- A chatbot with dashboards attached.
- A generic automation builder.
- A traditional SaaS application with an AI bubble added afterward.
- A collection of unrelated admin pages.

The target is a coherent AI-native operating environment.

# 3. Core product philosophy

Gravitre should support this operating loop:

Ask
→ Understand
→ Plan
→ Visualize
→ Modify
→ Approve
→ Execute
→ Observe
→ Learn

The user should be able to:

- Describe an outcome naturally.
- Let Gravitre interpret context.
- Receive an actionable plan or artifact.
- Inspect what Gravitre created.
- Modify it manually or conversationally.
- Approve consequential actions.
- Execute through governed systems.
- Observe progress and evidence.
- Learn from results.

AI should reduce unnecessary navigation and configuration.

AI must not eliminate useful direct-manipulation interfaces.

Gravitre must preserve advanced visual workspaces where they genuinely improve comprehension, inspection, editing, governance or control.

The target relationship is:

AI = primary intent layer.

Adaptive UI = contextual work surface.

Advanced workspaces = expert inspection and manipulation.

Do not collapse the product into chat.

# 9. Typography

Typography is mandatory and global.

## 9.1 Sentence case

Use sentence case throughout the product.

Correct:

- Health totals
- Workflow monitor
- Add connector
- Check live status
- Pending approval
- Model evaluation
- Intelligence overview
- Create workflow

Incorrect:

- HEALTH TOTALS
- WORKFLOW MONITOR
- ADD CONNECTOR
- PENDING APPROVAL
- MODEL EVALUATION

Proper nouns, acronyms and user-generated names retain correct capitalization.

Examples:

- Google Analytics
- HubSpot
- Microsoft 365
- AI
- API
- OAuth
- Salesforce
- Gravitre

Do not modify code identifiers or backend values simply for visual capitalization.

---

## 9.2 Typography scale

Audit the actual Nodus font and existing Gravitre tokens first.

Aim for a restrained scale similar to:

- Page heading: approximately 22–24 px / semibold.
- Section heading: 16 px / semibold.
- Component heading: 14 px / medium or semibold.
- Body: 14 px / regular.
- Secondary body: 13 px.
- Metadata: 12 px.
- Buttons: 13–14 px / medium.

Avoid:

- Excessive sizes.
- Too many weights.
- Uppercase tracking.
- Weak grey contrast.
- Large headings on operational pages.
- Repetitive subheading copy.

Use hierarchy through:

- Type.
- Spacing.
- Contrast.
- Alignment.

Do not use containers merely to create hierarchy.

- Approval state.

- Conversation.

### Expanded mode

## 17.2 Workflow Builder modes

Prototype four complementary modes.

### Design

For creation and editing.

Users can:

- Add nodes.
- Move nodes.
- Configure nodes.
- Connect nodes.
- Change conditions.
- Assign tools.
- Add approvals.
- Edit inputs and outputs.

### Live

For execution.

Display:

- Active node.
- Completed nodes.
- Waiting nodes.
- Failed nodes.
- Approval pauses.
- Current tool activity.
- Execution path.

Motion must communicate state.

### Explain

Allow inspection of:

- Why a node exists.
- What data it receives.
- What it outputs.
- Which agent/tool executes it.
- What evidence informed the step.
- Which approval governs it.

### History

For debugging and governance.

Show:

- Previous runs.
- Outcomes.
- Errors.
- Duration.
- Approvals.
- Changes.
- Retry history.

Only expose capabilities backed by the runtime.
