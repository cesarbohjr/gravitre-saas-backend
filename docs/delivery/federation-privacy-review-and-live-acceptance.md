## Implemented candidate adoption

The existing company-learning job retrieves the private aggregate for a currently consenting cohort member. Adoption reuses `company-retrieval-ranker`, the existing artifact format, registry, promotion gate and RAG consumers. No additional intelligence engine or activation switch is introduced.

Before dispatch, the source backend freezes the contributing deployed model/version reference in a bounded organization-settings ledger. After that timestamp it captures actual retrieval features, before feedback, only for a consenting organization with a verified program. No text, prompt, answer or document body enters those snapshots. A candidate needs 100 distinct later message-feedback cases, including at least ten of each label, within fourteen days. The first qualifying cohort is frozen by digest. Candidate and unchanged champion are evaluated against the same rows. Accuracy and AUC must not regress; AUC must beat chance; log loss must beat the champion and empirical-prior baseline. Feedback is a retrieval-helpfulness proxy, not causal business ROI or independently audited label truth.

Routine local ranker retraining pauses while this bounded benchmark is pending. Adoption rejects changed champions, changed candidates and changed benchmarks. It records registration intent before the existing registry write; uncertain writes require source readback instead of blind duplicate registration. Deployment uses a compare-and-swap on the current champion. Recovery verifies the actual deployed artifact's program/round provenance. Cached inference and RAG weights recheck federation permission; revoked or expired permission falls back without using that aggregate. Previously released differentially private aggregates and spent privacy budget cannot be recalled.

The additive migration `20261021050510_federated_ranker_observation_snapshot.sql` preserves legacy null rows and existing RLS/grants. It is prepared, **not applied**. The earlier registry-type compatibility migration is also still pending. No data is backfilled into a supposed future holdout.

## Independent reviewer scope

The accountable privacy/legal owner must select an independent qualified reviewer. The author must not certify their own implementation as independently approved. The reviewer must inspect the final source commit, immutable runtime image digest, SBOM/dependency audit, actual deployment configuration and node registry, then issue a referenced written assessment. A signed manifest is necessary technical evidence; possession of an Ed25519 key alone does not establish reviewer independence or legal approval.

| Boundary | Information and protections | Required independent assessment |
|---|---|---|
| Source backend → tenant node | Five canonical ranker coefficients encrypted to a distinct RSA 3072–8192-bit tenant key; source backend alone holds registry credentials | Key custody, canonical feature projection, confused-deputy and wrong-tenant refusal, artifact-source integrity |
| Tenant node → aggregation | Actual Flower 1.41 SecAgg+, organization-level replace-one Gaussian DP using PyDP, clipping and RDP composition; exactly 100 authenticated participants; no plaintext averaging fallback | Collusion/dropout assumptions, clipping/quantization effects, sensitivity 2C, noise independence, q=1 composition, release semantics and membership leakage |
| Runtime control and enrollment | mTLS, distinct node identities, signed deployment/feature/registry digests, metadata-only current-consent callback | CA issuance/revocation, tenant-to-node binding, replay/SSRF resistance, control-plane authorization and private network exposure |
| Durable privacy ledger | Per-tenant SQLite reservations and coordinator round state persist before releases; failed/uncertain releases retain expenditure | Volume durability, backups/restores, rollback resistance, crash/retry races, budget exhaustion and multi-instance serialization |
| Aggregate → existing registry | Private bounded JSON candidate, authorized cohort member only, tenant-local future holdout, champion CAS | Poisoning/inference risks, evaluation selection and label integrity, duplicate-registration recovery, expiration and revoked-consent behavior |
| Registry → artifact storage | Blob bearer destination bound to configured private store plus exact model/version path; no redirects; bounded download | Pickle trust/supply chain, model-writer access, store-token privileges, artifact tampering, cross-tenant authorization and key rotation |
| Consent and observations | Current program-specific federation and ranker permission; server disclosure version 3; snapshots omit content; no backfill | Notice adequacy, lawful basis, children/sensitive data, deletion/retention windows, withdrawal and already-released aggregate disclosure |

Open review decisions include actual threat actors/collusion threshold, chosen epsilon/delta/clipping/round limit, geographic processing locations, retention and deletion SLAs, legal owner, reviewer identity, image digest, enrollment registry and infrastructure account ownership. Engineering has not invented values or signoffs for these.

## Live verification procedure

1. Finish CI on the exact reviewed source. Build `backend/federated-runtime/Dockerfile`, retain SBOM and pin the resulting image by digest. Follow `backend/federated-runtime/README.md`; do not pass Supabase service-role, Blob or global provider keys into Flower processes.
2. Record the named governance owner's written purpose/budget/provider choices. Use the existing Intelligence permission dialog for the selected organization's approval; closing/defer is not permission. No script should grant permission or impersonate an owner.
3. Apply reviewed pending migrations through the established migration release process before enabling this program. Verify null legacy snapshots, CHECK constraints, RLS and org-scoped queries against the actual target. Existing user authorization to migrate persists; this packet adds no approval ceremony.
4. Use an actual authorized organization's session in `ML_VERIFICATION_SESSION`. Create a private JSON case file: `[{"model_id":"<existing UUID>","version":<deployed integer>,"inputs":[{<real eligible feature fields>}]}]`. Keep inputs/session out of git and reports. Run `python scripts/verify-existing-model-inference.py --expected-sha <deployed-main-SHA> --org <authorized-org-UUID> --cases /private/cases.json --report /private/inference-evidence.json`. It calls only health and bounded existing-model predictions, refuses redirects/unknown hosts and records metadata. Predictions write normal inference logs and may incur approved costs. No cases yields NOT RUN and nonzero exit, never inference PASS. This checks execution/shape/version, not accuracy or all-surface adoption.
5. Separately execute bounded image/audio/video cases through existing governed multimodal routes, domain training with the human-reviewed disjoint benchmark, and paid generation through canonical `platform_generate_image` with the real authorized actor. Retain redacted provider request IDs, policy revision, budget debit/reconciliation, verified storage/readback checksum, exact model/version and UI/text/voice trace. An API key name, health response or generic advisory prediction cannot satisfy these provider checks. Test consent withdrawal, missing budget, uncertain provider dispatch and private-storage failure without repeating paid dispatch.
6. Only after the independent review and program-specific tenant approvals, enroll at least 100 distinct real organizations with compatible deployed rankers and separate authenticated tenant compute/keys. Verify callback approval for each at contribution and release. Do not manufacture tenants or consent records to meet quorum. Backend/Redis alone is not this fleet.
7. In the real fleet demonstrate quorum/dropout refusal, mTLS/node identity rejection, privacy reservation across restart, exhaustion refusal, private candidate delivery restricted to participants, and tenant-local adoption/rejection after real future feedback. Capture aggregate metadata, never raw tenant samples/labels. Repeat inference through actual RAG/text/voice consumers and record fallback on withdrawal. A successful aggregate still does not prove adoption or business outcomes.

Release acceptance requires final CI URLs, merged/deployed SHA alignment, migration evidence, independent assessment/reference and signed manifest, consented enrollment evidence, actual provider receipts and per-surface inference traces.
